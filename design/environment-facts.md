| Headers URLSession adds | With an empty Headers table a GET goes out with `Host`, `Accept: */*`, `Accept-Language` (from the system languages, e.g. `en-GB,en-US;q=0.9,en;q=0.8`), `Connection: keep-alive`, `Accept-Encoding: gzip, deflate` (`gzip, deflate, br` over TLS) and `User-Agent: <process> CFNetwork/3896.100.1.1.1 Darwin/27.0.0`. A POST body with no `Content-Type` row also gets `Content-Type: application/x-www-form-urlencoded`, even a raw text body; DELETE, PUT and PATCH bodies get none (Body on GET), so the Headers table shows the row for POST only. Wire order is URLSession's, not the table's, though the table's rows keep their order among themselves. Measured against the echo server's raw bytes, GET and POST, HTTP and HTTPS, 2026-10-16 (`URLSessionFactsTests`). Every one can be replaced by setting it, even `Host` and `Connection`, and none can be removed: an empty value is sent as an empty header. The transport now replaces `User-Agent` and `Accept-Language` (sending.md) |
| Body on GET (Q6) | URLSession refuses it: a GET with the raw body `a=1` throws `URLError.dataLengthExceedsMaximum` (-1103, "resource exceeds maximum size") and the echo server receives no request at all, so the body is not dropped, the whole send fails. A GET with an empty body goes out as a plain GET with no `Content-Length`. A DELETE, PUT or PATCH with the body `a=1` is sent with `Content-Length: 3` and no `Content-Type`, so the form Content-Type URLSession adds on POST is not added on them (PUT and PATCH measured 2026-10-19). A HEAD with a body ended in `.timedOut` with nothing received; not looked into further. Measured against the echo server's raw bytes through `URLSessionTransport`, 2026-10-17 (`URLSessionFactsTests`). Curl Import has to warn on `-X GET -d …` |
| Manual Cookie header | Sent as set: with `httpShouldSetCookies = false` and no cookie storage, a `Cookie: manual=1` row arrives as `Cookie: manual=1`. A reply with `Set-Cookie` adds nothing to the next request. Measured against the echo server, 2026-10-16 (`URLSessionFactsTests`) |
| Response headers | No wire order and no duplicates. Two `Set-Cookie` replies arrive as one value `a=1; Path=/, b=2; Path=/` from both `allHeaderFields` and `value(forHTTPHeaderField:)`; `allHeaderFields` is a dictionary, so `Z-Last` before `A-First` is not recoverable. macOS 15 has no public API with the ordered list. Measured with the echo server's `/headers`, 2026-10-16 (`URLSessionFactsTests`) |
| Compression | URLSession decodes a `Content-Encoding: gzip` reply whatever was asked: with no `Accept-Encoding` row (wire: `gzip, deflate`), with `identity` and with `gzip`, the body arrives as the decoded bytes. An `Accept-Encoding` row replaces the default on the wire; an empty one is sent empty, not removed. `Response.byteCount` is the decoded size (16 bytes for a 36-byte gzip body), and the reply's `Content-Length` and `Content-Encoding` headers are kept. So a compression setting would have nothing to switch: it is never off, and Request Settings has none (design-system.md §9 Q10). Measured with the echo server's `/gzip`, 2026-10-16 (`URLSessionFactsTests`) |
| Cancelling a send | Cancelling the `Task` around `data(for:delegate:)` is the whole release. Against a reply delayed 10 s, cancelled at 1.055 s: the server saw the connection close at 1.059 s and the send returned at 1.061 s with `SendError.transport(.cancelled, "cancelled")`, one request recorded. Measured with the echo server's `/delay/10000`, 2026-10-16 (`URLSessionFactsTests`) |
| Large response memory | The transport's peak resident memory is about twice the body: 100 MB peaked at 246 MB (from 40 MB), 500 MB at 1,056 MB, received over loopback in 0.06 s and 0.25 s. URLSession gathers the body in chunks, then copies it into one `Data`. Showing it as text costs more on top. Accepted for v1 by the user, 2026-10-16: no cap. Measured with the echo server's `/bytes/<n>` and `getrusage` `ru_maxrss`, 2026-10-16 (`RACCOON_MEASURE=1 swift test --filter MeasurementTests`) |
| NSTextView with large bodies | Pretty-printed JSON, coloured from `Highlighter.ranges`, in a 900×700 window, debug build. TextKit 2 (the default, `NSTextView.scrollableTextView()`): 5 MB opens in 51 ms and every step is under 80 ms, but at 20 MB scrolling to the end takes 35.8 s coloured and 19.2 s plain, and a switch away 1.6 s. TextKit 1 with `allowsNonContiguousLayout`: 5 MB coloured opens in 24 ms, worst step 129 ms (scroll to the middle); 20 MB coloured opens in 67 ms, worst 477 ms; 20 MB plain worst 127 ms. Highlighting is about 110 ms per MB in a debug build and runs off the main thread (behavior.md). Replacing a large coloured `NSTextStorage`'s characters in place (`setAttributedString`) ran over 10 minutes at 1 MB without finishing; swapping in a new storage takes under 30 ms. Touching `layoutManager` on a TextKit 2 view silently falls it back to TextKit 1. Proposed from this: TextKit 1 non-contiguous for the body views, Pretty threshold kept at 5 MB. Measured 2026-10-16 (`RACCOON_MEASURE=1 swift test --filter TextViewMeasurementTests`) |
| Folding a large body | Same setup as above, TextKit 1 non-contiguous, pretty JSON coloured, debug build; 5 MB is 63,821 Fold Regions. **Hiding in the layout fails.** Zero-advance line breaks for the hidden lines merge a folded region into one line fragment, and CoreText typeset that line for over 10 minutes at 1 MB without finishing. Null glyphs with a zero-height line fragment per hidden line (`shouldSetLineFragmentRect`) do fold correctly (the next line sits right under the open line), and folding costs 4–18 ms at 5 MB, but non-contiguous layout keeps estimating the hidden lines at full height: with the root folded the view stays 1,144,767 pt tall. Laying them out for real costs about 1.9 s per MB (5 MB: 9.6 s for the root, 6.3 s folding the root while scrolled to the end); with items folded, scrolling to the middle took 147 ms. **Swapping in a display storage passes.** It holds the body with each Folded region replaced by " … ": at 5 MB, open 23 ms, fold the root 6 ms, Fold All 13 ms, unfold the root with every item still folded 67 ms, scroll to the middle 25 ms and to the end 16 ms, Unfold All 13 ms, fold one item 16 ms, fold 63 items 37 ms. Building it as a copy with replacements from the back is fast for a few folds; appending a large piece to a non-empty string is not (544 ms for one fold at 5 MB), so many folds are built by appending small pieces. Re-measured through the shipping code (`FoldRegion.find`, `FoldedText`, `ResponseViewer.cut`) at 5 MB: finding the regions 187 ms off the main actor, open 27 ms, Fold All 21 ms, unfold the root with every item folded 81 ms (the worst step), fold one item 22 ms, scroll 28 ms. 20 MB, never Pretty, worst 553 ms. Proposed from this and agreed: folding swaps in a display storage, with no size cutoff. Measured 2026-10-17 (`RACCOON_MEASURE=1 swift test --filter FoldMeasurementTests`) |

| Yaak `:name` in URLs | Read in source, not run. A placeholder is `/` then `:` then one or more characters that are not `/ ? # :` (`yaak/apps/yaak-client/lib/pathPlaceholders.ts`, `extractPathPlaceholders`), so `/tasks/:id:increment-importance` has the placeholder `:id` and the literal `:increment-importance`, and `/abc:def` has none. The value is a URL parameter row named `:id`, not a separate store; the UI derives a row for each name in the URL, one row for `:id` repeated. A row whose name left the URL **stays** in the model (the code's own comment says so). At send, `{{name}}` in the URL is rendered first, then `apply_path_placeholders` replaces `/:name` with `urlencoding::encode(value)` (`yaak/crates/yaak-models/src/path_placeholders.rs`, called from `yaak/crates/yaak-models/src/render.rs`). That encoder leaves only `A-Z a-z 0-9 - _ . ~`, so **`/` becomes `%2F`**, a space `%20`, and `%` `%25`. An empty value replaces the placeholder with nothing (the code skips only an empty *name*). A disabled row is not substituted. Match is literal and complete: `:foooo` is not `:foo`. Import: its Postman importer keeps `:id` in the URL and writes each `url.variable` as a URL parameter `:key` with the value, disabled included (`yaak/plugins/importer-postman/src/index.ts`, `convertUrl`; fixture `plugins/importer-postman/tests/fixtures/params.output.json`: `example.com/:foo/:bar`, rows `:foo` = `fff`, `:bar` = `bbb`); the Bruno importer maps `type: "path"` params the same way (`plugins/importer-bruno/src/body.ts`, `urlAndParams`, test at `tests/index.test.ts:58`); the curl importer does nothing with `:name`. Its Copy as Curl plugin reads `urlParameters` only as a query string (`plugins/action-copy-curl/src/index.ts:35`); whether the request it receives is already rendered was not checked |
| Bruno `:name` in URLs | Read in source, not run. A Path Variable is a path segment that starts with `:`; the name is everything after it up to the next `/`, so `:id.json` is the name `id.json` (`bruno/packages/bruno-app/src/utils/url/index.js`, `parsePathParams`, spec lines 26-46: `/:id/:` gives only `id`, `/:id/posts/:id` gives `id` once). The URL's authority is not scanned (`bruno/packages/bruno-common/src/generate-code/har/index.ts`, `hashPathParamPositions`; `1.1.1.1:3000:id` is no param, spec line 413). It also reads OData `Entity(:key)` forms, which Raccoon does not. Values live in `request.params` with `type: "path"`, alongside the query params, in the `.bru` file as `params:path`. Typing in the URL **drops** the path param of a name that left it (`collections/index.js` around line 1223, "remove path param that not used or deleted when typing url"), and keeps the value of a name that stays. At send (`bruno/packages/bruno-electron/src/ipc/network/interpolate-vars.js`, around line 181) the value is `{{}}`-interpolated, then written **raw** into the path, so a `/` in it is a new segment; then, if the request's `encodeUrl` setting is on (default true for new requests), the whole URL goes through `encodeUrl` (`bruno/packages/bruno-common/src/utils/url/index.ts`), which encodes each path segment but never the `/` between them. The code-generation path differs: it substitutes `encodeURIComponent(value)` when `encodeUrl` is on, so the snippet shows `aaa%2Fbbb` for a value `aaa/bbb` (`har/index.spec.ts` matrix, "issue #7356"; `url/index.spec.ts` line 507) while the send, read in source, puts `aaa/bbb`. An empty or whitespace-only value, or a missing one, keeps `:name` as typed (`hasResolvablePathParamValue`). Import: `postman-to-bruno.js` line 764 turns each `url.variable` with a key into a `type: "path"` param with its value and keeps `:id` in the URL; a variable with no key is dropped |
| Postman `:name` in URLs | **Read in the open-source libraries, not seen in the app.** Fetched 2026-10-28 from `postmanlabs/postman-collection` `lib/collection/url.js` and `postmanlabs/postman-url-encoder` `encoder/index.js` (neither is vendored under `bruno/` or `yaak/`), through a summarising fetch, so quote neither as verbatim. A path segment that starts with `:` is a variable, and its key is the text after `:` **up to the first `.`**; the rest of the segment is kept, so `/:id.json` with `id` = `5` is `/5.json`. `getPath()` replaces the segment only when the variable's value is a non-empty string, so an **empty value leaves `:id` in the URL**. The value is inserted **without encoding** in `url.js`. The URL is then encoded by `postman-url-encoder`, whose path set encodes controls, space, `"`, `#`, `<`, `>`, `?`, backtick, `{` and `}` and **does not encode `/`** (`encodePath('foo/bar&baz')` returns `foo/bar&baz`). So a Postman Path Variable value `a/b` is sent as two segments. Whether `%` is re-encoded was not seen: Postman users type `%2F` to send a slash, which only works if an existing `%XX` is left alone. That is inference. The Postman app's own behaviour was not run here |
